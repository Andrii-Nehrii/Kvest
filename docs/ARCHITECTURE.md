# Kvest — архитектура и план беты

Текстовый квест о постепенном зомби-апокалипсисе на севере Германии для двух реальных игроков
(A — Android, B — iPhone). Документ для разработки и для тех, кто будет дописывать главы.
Закрытые законы мира — в `docs/hidden/WORLD_BIBLE.md` (игрокам не читать).

## 1. Главные решения

| Вопрос | Решение | Почему |
|---|---|---|
| Платформа | PWA: TypeScript + React + Vite | Один код для Android и iPhone, бесплатная установка «на экран», без магазинов |
| Хостинг | GitHub Pages (HTTPS, бесплатно) | Service Worker и установка PWA требуют HTTPS |
| Офлайн | Service Worker кэширует всё приложение; состояние — IndexedDB | Между контрольными точками интернет не нужен |
| Сюжет | Данные (TS-модули со сценами), не код интерфейса | Новые главы добавляются без переделки движка |
| Синхронизация | Обмен **подписанными журналами действий**, а не состояниями | Чужие решения нельзя перезаписать; повтор даёт тот же мир |
| Транспорт | Код через мессенджер (кнопка «Поделиться») или автоматически через ветку `saves` на GitHub (токен на телефоне) | Без своего сервера; облако — по желанию |
| Случайность | Детерминированная: хэш(сид пары, игрок, номер броска) | Одинаковые результаты на обоих телефонах |
| Онлайн-сервисы | Не нужны для игры | Всё работает офлайн |

## 3. Модель мира и детерминизм

* Всё состояние (`GameState`) — простые данные JSON. Хэш состояния (`stateHash`) — от канонического
  JSON, поэтому «одинаковый мир» можно проверить сравнением 8 символов на экранах обоих телефонов.
* Переменные: `w.*` — объективный мир, `A.*`/`B.*` — персонажи, `$.*` в сценах — «текущий игрок»,
  `joint.<id>.*` — итоги совместных решений.
* Объективный мир ≠ знания персонажей. `knowledge[A|B]` хранит факты, слухи, догадки и ложь
  (`fact | rumor | guess | false`) с источником и временем. Интерфейс показывает только знания игрока.
* Случайность: `roll()` = хэш(сид пары, игрок, номер броска, метка). У каждого игрока свой счётчик,
  поэтому участки независимы и воспроизводимы.
* Новые объекты получают id с префиксом игрока (`it-A17`, `it-B17`) — без коллизий при слиянии.

## 4. Действия

* **Сцена** — текст (блоки с условиями), действия, эффекты при входе, флаги `safe`/`calm`, номер КТ.
* **Действие** — длительность, тип нагрузки, условия видимости/доступности (с причиной), эффекты,
  исходы (условные, вероятностные, с проверкой навыков), переход в другую сцену.
* **Типы**: одиночное; совместимое (`combinable`); взаимоисключающие (`group`); последовательное
  (`requiresDone`); условное (`when`/`enabled`); рискованное (`risky` + исходы с проверкой);
  уводящее из сцены (`terminal`/`goto` — в плане только последним).
* **План из нескольких действий** («1, 3, 4»): игрок отмечает варианты, меняет порядок, движок
  проверяет совместимость (`validatePlan`), затем выполняет по шагам (`executePlan`). Перед каждым
  шагом мир проверяется заново: если после шага 1 шаг 2 стал невозможен, исход изменил сцену,
  событие прервало план или персонаж потерял сознание — выполнение останавливается с объяснением.
* **Переходы** (действия, уводящие из сцены) при сборке сюжета становятся повторяемыми и совместимыми,
  если в сцене не указано иное (`repeatable: false`): «собрать рюкзак, потом выйти» — один план.
* **События с прерыванием** (стук, крик) обрывают отдых, сон и ожидание; начатое дело (поездка, очередь,
  работа) доводится до конца, а останавливается только остаток плана.
* **Проверка навыка**: шанс = 0,5 + (среднее черт × 2 × текущие способности + бонусы − сложность) × 0,1,
  в пределах 2–98 %. Усталость, недосып, боль, кровопотеря, жар снижают способности → шансы.
* **Универсальные действия** (там, где сцена их разрешает): попить, поесть, перевязать (бинт/тряпка;
  с антисептиком — полноценно), обезболивающее, новости в телефоне, SMS партнёру, передышка, сон
  (только в безопасном месте). Это даёт свободу без онлайн-сервисов.
* **Свободный текст** не поддерживается и не будет заявлен. Свобода — через
  контекстные действия, комбинации и универсальные механики.

## 5. Тело, время, ресурсы

* Тело (`body.ts`): голод, жажда, усталость, недосып (часы), кровопотеря 0–100, температура тела,
  стресс, раны (вид, место, тяжесть, кровотечение, обработка, бактериальное заражение, заживление),
  болезни, сознание (`awake/asleep/unconscious/coma/dead`), лекарства.
* Способности (`mobility`, `focus`, `strength`) выводятся из тела. Перелом ноги режет подвижность до
  четверти, перемещения (`move`) соответственно длятся дольше.
* Пороги: кровопотеря ≥ 55 — без сознания, ≥ 78 — кома, 100 — смерть; температура < 30 — без
  сознания, ≤ 26 — смерть; 48 ч тяжёлого обезвоживания — смерть. Раны мелкие сворачиваются сами,
  тяжёлые — нет. Через сутки решается (детерминированно) бактериальное заражение раны.
* Среда: погода по региону и часу, мокрая одежда, утепление по слотам, отопление/ток в помещении.
* Время идёт шагами по 15 мин: тело, батареи (телефон садится), события мира и планы NPC.
  Мгновенных перемещений нет: длительность пути задаётся сценой по реальным расстояниям (§12).
* Предметы — экземпляры с количеством, весом, износом, зарядом и местом
  (`у игрока / в месте / у NPC / в контейнере / израсходован`). Оставленное лежит там, где оставили.
  Перегруз > 125 % комфортной нагрузки (10 кг + 2,5 кг × сила) повышает усталость.
* Бытовые правила (`StandingRules`): заряжать телефон от бесплатной розетки (если есть зарядка),
  пить/есть в спокойной обстановке, не трогать «резерв». Сюжетных решений они не принимают.

## 6. NPC и события мира

* NPC: цели/страхи/тайны (скрытые), место, статус, доверие к каждому игроку отдельно, память
  («B:plan=evac»), собственный план (`agenda`): пункты по времени и условиям, выполняются сами,
  независимо от игроков (например, семья уезжает с фермы в 18:00, если ей не доверяют).
* События мира (`events`) — хронология катастрофы. Объективные эффекты одинаковы на обеих линиях
  (только `set`, поэтому повторное срабатывание безвредно). Новости доходят только по доступному
  каналу: телефон с сетью, радио/ТВ, люди вокруг, своими глазами. Пропущенные новости в телефоне
  можно прочитать позже.

## 7. Контрольные точки и синхронизация

Порядок (п. 9.1 задания):

1. Оба начинают с одного состояния (хэш совпадает).
2. Каждый играет участок офлайн. Сохраняется **журнал планов** (`ActionRecord[]`) и текущее состояние.
3. Сцена с `checkpoint: N` (или смерть/потеря сознания) завершает участок; дальше — блокировка.
4. **Фаза 1 — журналы.** Телефон формирует `SegmentPacket` (журнал, хэш начала и конца, версии,
   подпись HMAC-SHA256 секретом пары) → код `KVEST1.…` → «Поделиться» в мессенджер.
   Партнёр вставляет код. Каждый телефон **сам воспроизводит** журнал партнёра от общего состояния
   и сверяет хэш конца. Подмена, чужая пара, другая версия сюжета — отказ с понятной причиной.
5. Слияние (`mergeSegments`) симметрично — порядок прихода пакетов не влияет:
   * свой персонаж, свои знания, свой счётчик случайности — из своего участка;
   * переменные мира: изменил один — берётся его значение; изменили оба — правило ключа:
     `delta` (сложить изменения), `latest` (позже по игровому времени), `max/min/or/and`;
     ничья — хэш ключа (без приоритета игрока);
   * NPC: доверие к A — из участка A, к B — из участка B; память и выполненные пункты — объединение;
     смерть необратима;
   * предметы: изменил один — его версия; оба — позднейшая по игровому времени.
6. Сведение часов: отставший персонаж «проживает» время до общего момента (ест/пьёт/мёрзнет).
7. Доставка SMS: сообщения, отправленные офлайн, приходят, если телефон получателя жив и есть сеть.
   **Звонки между игроками посреди участка невозможны технически** (партнёр офлайн), поэтому живой
   разговор персонажей происходит только на контрольной точке, а в участке — «сеть перегружена /
   не отвечает». Это осознанное ограничение.
7а. **Заметки после слияния** (`CheckpointDef.onMerge`): каждый игрок видит свою версию — дозвонились ли
   (`callable`: оба телефона живы и есть голос; на КТ 1 — ещё и «оба набирали»), встретились ли
   (`partnerAt`), что узнали друг от друга (`partnerKnows` → `learn`). Тексты, которые видят оба, пишутся
   с подстановками `{A}`, `{B.gen}`…
8. **Фаза 2 — совместные вопросы.** Каждый отвечает на своём телефоне → `AnswersPacket` → обмен.
9. `completeCheckpoint` решает вопросы, разводит игроков по следующим сценам, проверяет поражение.
   Итоговый хэш показывается на обоих экранах для сверки.

Повторная отправка того же пакета ничего не меняет. Новый пакет с тем же номером КТ от того же
игрока, но с другим журналом, будет отклоняться (защита от «переигрывания» — в слое сохранений, этап 5).

**Облако через GitHub (вместо Firestore, решение владельца 29.10):** ветка `saves` этого же
репозитория. На телефоне один раз вводится fine-grained токен (доступ только к Kvest, Contents:
Read and write); в коде сайта токена нет. Телефон сам кладёт:
* `pairs/<pairId>/save-<A|B>.json` — сохранение (на КТ, при смене фазы и каждые 5 действий);
* `pairs/<pairId>/kt<N>-hod-<A|B>.txt` и `kt<N>-otvet-<A|B>.txt` — коды КТ; код партнёра
  забирается сам (проверка каждые 12 с, пока открыт экран точки).
Каждый телефон пишет только свои файлы. Ручной обмен кодами остаётся запасным.
Сохранения из облака читаются сценаристом для глав «под прохождение» (`git fetch origin saves`).

## 8. Совместные решения (`resolveJoint`)

1. Участники — те, кто в сознании и имеет отношение к вопросу (`canParticipate`). У каждого свой
   текст вопроса (разные знания).
2. Одинаковые ответы → выполняется, если объективно возможно (`feasible`).
3. Совместимые (`compatible`) → выполняются оба, если хватает ресурсов/условий.
4. Частично совместимые → компромисс (`compromises`) только при выполнении его условия.
5. Несовместимые → внешнее обстоятельство (`arbiters`): условие на мир, существовавшее заранее
   (погода, топливо, NPC, ранее начавшееся событие). Порядок — по объективной силе, не по игроку.
6. Если ни одно обстоятельство не сработало — взвешенная случайность с объективными весами;
   бросок от хэша (сид, id решения) сохраняется в истории и воспроизводится.
7. Невыполнимый выбор → `default` («всё осталось как есть»).
8. Намерения сохраняются: `joint.<id>.A/B`, память NPC (`rememberedBy`) — влияют на доверие дальше.
9. Один участник (второй без сознания/мёртв) → решает он один; ни одного → решает мир.

## 9. Недееспособность, спасение, смерть, поражение

* Без сознания/кома: участок игрока заканчивается. На КТ его ведёт партнёр (`controlledBy`):
  тело недееспособного продолжает жить по физиологии на линии партнёра (кровь, холод, жажда).
  Спасение — обычные сцены партнёра: дойти, найти лекарства/врача/транспорт, обработать раны
  (`treat` с `target: '@partner'`). Успех не гарантирован.
* Очнувшийся персонаж возвращается в игру со следующей КТ; прошлое партнёра он не меняет.
* Смерть одного — игра продолжается для второго; воскрешения нет.
* Оба не могут действовать → честная промотка времени до 14 дней (с уходом NPC, только если он
  заранее рядом: `X.caredBy`). Очнулся кто-то — игра продолжается; оба погибли или помощи нет —
  **окончательное поражение** и итоговая история (длительность, причины, решения, судьбы NPC).

## 10. Сохранения и совместимость

* IndexedDB: общее состояние последней КТ, журнал текущего участка, текущее состояние, входящие/
  исходящие пакеты, секрет пары. После каждого плана — автосохранение.
* Экспорт/импорт файла сохранения и напоминание о резервной копии на каждой КТ
  (браузерное хранилище iOS может очиститься; `navigator.storage.persist()` запрашивается).
* Версии: `schema` (формат сохранения), `engineVersion`, `contentVersion`. Новые главы **только
  добавляют** сцены/переменные/события; id прошлых сцен, предметов и переменных не переименовываются.
  Если формат меняется — миграция `schema N → N+1`. Партнёры должны иметь одну версию сюжета на КТ
  (приложение обновится само при подключении к интернету).
* **Обновление посреди игры** (`refreshSave` при открытии): `upgradeState` довозит новых NPC, начальные
  переменные и предметы с `key`; свой участок пересчитывается текущей версией — так же, как его посчитает
  партнёр; если сыгранное действие стало невозможным, участок обрезается с предупреждением.
  Хэш мира не включает тексты (журнал, тексты сообщений), поэтому правка формулировок безопасна.
  В кодах КТ едет отпечаток сборки (`contentBuild`): разные сборки — просьба обновиться обоим.
* **Эталонные журналы** `src/content/fixtures/release-N.json` (тест `compat.test.ts`): сыгранные на
  выпущенной версии участки должны повторяться бит в бит. При выпуске новой главы добавляют `release-N+1`
  (`KVEST_FIXTURE=release-N+1 npx vitest run src/content/compat.test.ts`) и вписывают в список `releases` теста.
* **Пока игра тестовая** (владелец не объявил начало настоящей партии), сыгранное можно менять: исправления
  механики действуют сразу, а эталонный журнал пересоздаётся (удалить `release-1.json` и пересоздать командой
  выше). **Когда настоящая игра началась**, журналы не перегенерируют, а исправление, меняющее расчёт
  сыгранного, включают по номеру контрольной точки (`s.checkpoint >= N` — с участка, который ещё никто не играл),
  чтобы прошлые участки, слияния и сведение часов считались по-старому бит в бит.
* Облако: из меню можно восстановить игру из ветки `saves` (если телефон очистил данные).

## 11. Скрытая информация

Секреты мира (законы инфекции, планы NPC, будущие события) лежат в коде офлайн-приложения —
абсолютно спрятать их нельзя. Разумные меры: интерфейс показывает только знания персонажа и
симптомы (не названия болезней), главы подгружаются по мере открытия, закрытая документация
не входит в сборку. Договорённость: не читать `docs/hidden/` и исходники сюжета.

## 12. География (реальные данные, проверять перед использованием в механике)

Время пути — в обычных условиях; в кризис его меняют события (пробки, перекрытия).
Список маршрутов, применённых в бете, ведётся в `src/content/routes.ts` с источником.

## 13. План первой беты

Подробный дизайн (персонажи, старт, NPC, ветки) — в `docs/hidden/STORY_DESIGN.md` (спойлеры).

* Персонажи: A — 184 см / 88 кг, хорошая форма, бокс в прошлом; B — 167 см / 50 кг, не сильная,
  немного занималась в зале. Физические черты фиксированы, остальные — правятся при создании.
* Старт — вторник 10.11.2026, 06:30, дождь и туман. A — в небольшом городе южнее Гамбурга,
  B — в квартире в Гамбурге. С первой минуты тревожно, но никто не знает, что происходит.
* **Участок 1** (35–50 мин на игрока, ~06:30–12:30): соседи, новости, первые решения о ресурсах и людях.
* **КТ 1** (~12:30): первая связь, совместный вопрос «как встречаемся».
* **Участок 2** (35–50 мин, день → ночь): дорога, город рушится, доверие незнакомцам.
* **КТ 2** (ночь/утро): где переждать ближайшие дни — конец первой арки.
* Главы 2+ — режим базы (дни 2–4 и дальше): запасы, дежурства, соседи, обмен, ремонт, топливо.
  Убежище не гарантировано; можно остаться в городе, разделиться, потерять всё.

### Режим базы (движок, `base.ts`)

* База — набор локаций с общим складом (`BaseDef`). В 06:00 жильцы (NPC + игроки на месте) тратят
  воду (л/чел.), еду (ккал/чел. из «основных» продуктов, сначала скоропортящиеся) и дрова (по погоде).
  Нехватка копится в `base.<id>.shortDays` — NPC на неё реагируют.
* Суточный расход считает линия игрока, бывшего на базе в начале участка; если таких двое —
  выбирает хэш дня; если никого — досчитывается на КТ. Двойного расхода не бывает.
* Если оба игрока брали из одного запаса в своих участках — при слиянии расход складывается.
* Транспорт: бак в литрах, расход л/100 км, вид топлива; канистры; не то топливо губит двигатель.
* Долгие работы (`ProjectDef`): часы, нужные детали, проверка навыка каждый час (неудачный час —
  половина зачёта), награда по завершении. Деталь может не подойти — это решает сюжет.

## 15. Как добавлять главы

1. Прочитать этот документ, `docs/hidden/WORLD_BIBLE.md` и `docs/hidden/STORY_STATE.md`
   (переменные, незакрытые линии, прошлые решения).
2. Создать `src/content/chapterN/` со сценами для A и B (каждая сцена — `for: 'A' | 'B'`),
   новые события мира (только `set`-эффекты), новые NPC, совместные решения, `CheckpointDef`.
3. Не менять законы возбудителя, хронологию прошлого, id существующих сцен/переменных/предметов.
4. Каждое внешнее обстоятельство для несовместимых решений должно опираться на переменную или
   событие, которое существовало **до** контрольной точки.
5. Поднять `contentVersion`, прогнать `npm test` (сюжетный линтер проверит ссылки, достижимость,
   минимальную длительность участков).
