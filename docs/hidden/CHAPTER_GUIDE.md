# ЗАКРЫТО ДЛЯ ИГРОКОВ — как пишется новая глава (процесс, устройство, проверки)

Голос и стиль — `WRITING_GUIDE.md`. Законы мира — `WORLD_BIBLE.md`. Что уже случилось и какие флаги есть — `STORY_STATE.md`.
Образец устройства главы — `src/content/chapter2/` (повторять его приёмы, а не изобретать новые).

## 0. Порядок работы (строго по шагам)

> **Главное — качество, а не скорость.** Глава пишется **частями** (§8): одна часть — одно место за один участок
> (например «хутор, участок 5») или КТ с её решением. Каждая часть доводится до уровня глав 1–2 и проверяется
> циклом §8 (тест качества + стенограмма, прочитанная целиком + самооценка), и только потом начинается следующая.
> Лучше три части уровня глав 1–2, чем вся глава уровнем ниже. Владелец не торопит.

1. **Прочитать:** `CLAUDE.md`/`AGENTS.md`, `docs/ARCHITECTURE.md` (§3–§10), `docs/hidden/*`, весь `src/content/chapter2/`,
   `src/content/chapter2.test.ts` — **один раз**; дальше память — `docs/hidden/CONTEXT.md`. Сохранения пары (`git fetch origin saves:refs/remotes/origin/saves`, `pairs/<id>/save-A|B.json`):
   где они, что знают, что с NPC — чтобы самая вероятная их линия была самой проработанной. Где пара ещё может
   оказаться — `pairpaths.test.ts` (`CONTEXT.md` §4): писать только эти места.
2. **План — файлом** `docs/hidden/CHAPTER<N>_PLAN.md` до кода:
   * хронология дня: события мира (время, что меняют), планы NPC (время, условия), сроки болезней укушенных (WORLD_BIBLE);
   * **матрица стартов**: все места, где игрок может оказаться после прошлой КТ (по её `next` и сценам), вместе/порознь —
     и для каждого: какая сцена, что там делать, как дойти до следующей КТ;
   * участки (обычно 2 на игровой день: до ~середины дня и до ночи), их КТ: заметки при слиянии, совместное решение
     (варианты, объективная выполнимость, компромиссы, арбитры), `next`;
   * новые места, предметы, факты, NPC, флаги — со списком, кто их ставит и кто читает.
3. **Код** в `src/content/chapter<N>/` (как в главе 2): `world<N>.ts` (места, факты, NPC, планы NPC, события, радио, зоны),
   файлы сцен по участкам, `kt<N>.ts` (КТ и решения). Подключение — в `src/content/index.ts` (сцены, факты, события,
   `withAgenda`, `joint`, `checkpoints`). `next` прошлой КТ — на новые сцены (если её ещё никто не прошёл).
4. **Тесты** (§5), затем **цикл качества** (§8) по каждой части и **самопроверка по чек-листу** (§6) — честно, по каждому пункту.
5. `npx tsc --noEmit && npx vitest run` — всё зелёное; затем `npm run e2e:quick` и сценарий `codes` на все КТ.
6. Коммит в свою ветку, PR в main **без слияния** (сливает владелец после проверки). Отчёт владельцу — без сюжета (§7).

## 2. Устройство сцены (шпаргалка)

```ts
S({ id: 'c5_xxx', for: 'any', chapter: 'ch3', location: 'hof_luedemann', title: 'Короткий заголовок', safe: true,
  text: [{ when: AM, text: '…' }, { when: { all: [EVE, withPartnerAt('hof_luedemann')] }, text: '…' }],
  actions: [
    { id: 'c5_talk', label: 'Поговорить с Хенрике', minutes: 15, combinable: true, when: notDone('c5_talk'),
      text: '…', effects: once('c5_talk', [{ npc: 'henrike', trust: 4 }]) },
    { id: 'c5_go', label: 'Ночь. Устроиться на ночлег', minutes: 5, terminal: true, goto: 'c6_cp6', when: { all: [C5, after(20, 0)] } },
  ] })
```
* Id сцен и действий главы — со своим префиксом (`c5_…`), не пересекаться с прошлыми.
* Хаб-сцена места: тексты на каждое время суток (NIGHT / AM / PM / EVE) — нет «утренних» фраз днём; действия с окнами времени.
* `safe: true` — можно спать (универсальное «Лечь спать»); `calm` — бытовые правила без сна; `universal: false` — без
  «попить/поесть» (КТ-сцены, острые сцены). `ambient` — если игрок в машине/под крышей вне помещения.
* Переход к КТ — последним в списке; толчок-событие за час-два до конца участка (как `ev2_cp3_push`).
* Каждая хаб-сцена: есть «переждать час» (`waitHour`) и выход; нет тупиков (тест ловит 80–90 действий в одной сцене).

### Условия (`Cond`) — частые
`{ at }`, `{ partnerAt }` (партнёр в твоей линии стоит там, где был на КТ), `{ flag: '$.x' | 'w.x' | 'A.x' }`, `{ v, op, value }`,
`{ has }`, `{ hasTag }`, `{ npc, at, status, alive: true, trust: ['>=', n] }`, `{ npcVar, key, value? }`, `{ knows }`,
`{ before | after: at(day, h, m) }`, `{ me: 'A' | 'B' }`, `{ cp: N }`, `{ itemAt, place }`, `{ fuelFor, km }`, `{ fuelIn, liters }`,
`{ injured, minSeverity }`, `{ body: 'coreTemp', op, value }`, `{ stocked, qty, at }`, `{ callable: true }`, `{ partnerKnows }`.
**`{ npc, at }` не проверяет, жив ли NPC** — добавлять `alive: true`.

### Эффекты — частые
`set`, `add`, `give` (можно `fuel`), `take`, `takeTag`, `use: 'dressing'`, `pickup`/`drop`, `place`, `stock`/`unstock` (с `at`),
`body: { stress|fatigue|hunger|thirst, delta }`, `injure` / `biteArm(site, severity)` (риск через одежду), `treat`, `learn`, `move`,
`npc: { trust, remember, set, status, moveTo, alive }`, `wait`, `sleep`, `drive`/`driveTo(km, to, jam)`, `refuel`, `fillCan`, `siphon`,
`work` (проекты), `if/then/else`. Поездка: **сначала игрок у машины** (`toCar`), потом `drive` с `to` — `move` после; при нехватке
бензина `drive` не переносит — всегда есть запасной путь пешком.

### События и планы NPC
* `events`: `scope: 'world'` — у обеих линий, эффекты **только `set`** (линтер); личные — `scope: 'A'|'B'`. `interrupt` — будит,
  прерывает план. `news` — по каналу (direct/radio/phone/people); **в тексте новостей без шаблонов**. Окна `before`, иначе
  событие сработает с опозданием у того, кто пришёл позже.
* Что должно случиться без игрока (NPC укусили, уехал, обратился) — **пункт плана NPC** (`agenda`, `withAgenda` в index.ts),
  а не событие у игрока. События — только чтобы игрок это увидел/услышал.

## 3. Два телефона (самое важное)

* Каждый участок каждый играет на своём телефоне; на КТ линии сливаются (`mergeSegments`): своё тело/знания — из своей линии,
  мир — «изменил один → его значение, оба → позднее», количества и топливо — сумма изменений.
* **Вместе в одном месте** (`w.together` + одно место):
  * машиной и бензином распоряжается **только линия A** (у B — просто `move`); расход ресурсов — у одной линии;
  * судьбу NPC в «своём» доме решает хозяин места (`{ me }`), гость — помогает/говорит;
  * далеко не уходить и не менять маршрут — куда идти, решается на КТ; развилки общей дороги — **только объективные**
    (время, бензин, флаги проверки с КТ), а выбор каждого меняет его самого (тело, вещи, отношения);
  * исход, который должен быть одинаковым у обоих, — вычислить на КТ (заметка `onMerge` или эффект решения) и читать флагом.
* **Порознь**: каждый может идти к другому; приход к двери — сразу на КТ (`$.at_partner_door…`), встреча решается заметкой КТ.
* Заметки КТ применяются **сначала к A, потом к B на общем состоянии**: если эффект заметки меняет флаг, которым проверяется
  заметка B, — ставить личный флаг (`$.ktN_found`) и проверять партнёра через `@partner.`.
* Решение на КТ: выполнимость (`feasible`) — объективная, от лица мира (ctx A: `at` — где A, `partnerAt` — где B); порознь
  разные ответы → компромисс «остаёмся»; вчерашний план побеждает в споре только вместе; `default` — выполнимый вариант.

## 4. Темп и объём (обязательные нормы)

* **Два участка на игровой день** (утро → ~середина дня, КТ; день → ночь, КТ), как в главах 1–2. Участок длиной в целый
  день — нельзя: он неизбежно становится рутиной.
* Участок: ~35–50 минут игры на игрока, **50–70 решений** при обычной игре; в начале — 2–3 сильные ситуации, дальше — жизнь места.
* **Объём:** ориентир — как глава 2: ~2000 строк сюжетных данных на игровой день. Заметно меньше — признак, что места
  описаны заготовками.
* Каждое место, где игрок может провести участок, — полноценное: свои тексты на каждое время суток, 8–15 действий,
  своё вечернее/ночное событие, люди с характером. Главная вероятная линия пары (по сохранениям) — самая богатая.
* **В каждом участке — минимум два события с прерыванием**, которые ставят игрока перед выбором с ценой (опасность без боя,
  просьба о помощи, конфликт между людьми, нехватка), и последствия этих выборов — флагами для будущего.
* **Запрещено:**
  * один и тот же текст в разных местах (общая заготовка «ночь» для всех хабов) — у каждого места своё;
  * второй день главы из тех же действий, что первый, с подменённым текстом — новый день = новые ситуации из хронологии мира
    и последствий прошлого дня;
  * совместное решение на КТ про абстрактный «приоритет» — решение должно менять, **где** вы, **с кем** вы или **что у вас есть**
    в следующем участке (как `meet`, `shelter`, `day2`), 3–6 вариантов, хотя бы один тяжёлый размен.

## 6. Чек-лист самопроверки (ошибки, которые реально находили при проверках)

- [ ] Мёртвый NPC «стоит» на месте и с ним можно взаимодействовать (`alive: true` в условиях).
- [ ] Поездка: игрок не у машины → `drive` не работает; `move` до `drive` бросает машину; нехватка бензина → тупик без пешего пути.
- [ ] Один игрок попадает в чужую квартиру без ключей / без хозяина.
- [ ] Текст обещает действие, которого нет («можешь ехать дальше один»).
- [ ] Утренний текст днём, «темнеет» вечером, «мокрый» после дождя, «она засыпает» днём — окна времени у текстов и действий.
- [ ] Событие должно случиться без игрока — сделано событием у игрока (не срабатывает, если его нет рядом).
- [ ] Последствие наступает, когда игрок уже вмешался (проверять сцену/флаг вмешательства).
- [ ] Одно и то же решение принимают обе линии (судьба NPC, расход бензина, отъезд) — оставить одной линии.
- [ ] Заметки КТ: второй игрок не видит встречи/новостей из-за порядка применения.
- [ ] Решение КТ: порознь при разных ответах выигрывает «вчерашний план» вместо «остаёмся»; «туда же» невыполнимо для тех, кто уже там.
- [ ] Персонаж знает то, чего не узнавал (имена, детали чужой линии).
- [ ] Род: «ты видела» в общей сцене, `{pm:смотрит|смотрит}`; шаблоны в новостях событий.
- [ ] Каждая хаб-сцена: выход есть в любое время; переход к КТ доступен; нет 80+ действий без смысла.
- [ ] Всё новое за `{ cp: N }`; `compat.test.ts` зелёный; сохранение пары из облака повторяется (`refreshSave` без обрезки).
- [ ] Сцена в доме, ночлег, погреб в месте с `indoor: false` (хутор — это двор) без `ambient` — персонаж мокнет и мёрзнет у печки.
- [ ] Хозяйственные дела и разговоры доступны ночью (02:00 «подержать куртку») — окна времени у действий.
- [ ] Флаг «на будущее», который никто не читает; исход эпизода, о котором больше нигде не вспоминают.
- [ ] Сильное событие (вспышка, обращение знакомого) решено одной сценой и сразу сменилось бытом.
- [ ] `quality.test.ts` зелёный; стенограммы главной линии прочитаны целиком (§8).

## 8. Качество: работа частями и цикл самопроверки (так проверяет ревьюер — делай то же самое сам)

### 8.1. Порядок частей

1. Только места из `transcripts/pair-paths.txt` (`pairpaths.test.ts` по настоящим сохранениям), сверху вниз, участок за
   участком. Потом остальные места — тоже по одному. КТ с решением — отдельной частью, когда готовы все места участка.
2. Пока место не дописано, его сцена-хаб может быть короткой «рабочей» (выход + переход к КТ), но в main такая глава не идёт.
3. Каждая часть — отдельный коммит «Глава N: часть K» в ветку главы; PR обновляется. Отчёт владельцу — без сюжета.

### 8.2. Цикл одной части (повторять, пока все оценки ≥ 4)

1. **План части** — в `CHAPTER<N>_PLAN.md` таблицей: 2–3 события (время из хронологии мира/планов NPC; кто участвует;
   варианты и **цена каждого**; где и кто вспомнит исход — сцена/текст/заметка КТ/решение КТ/следующий участок),
   чем вечер отличается от утра, чем этот день отличается от прошлого, 8–15 действий места (у каждого — человек или последствие).
2. **Написать** сцены вручную в стиле главы 2 (`S({…})`, `at(д, ч, м)`, именованные условия). Никаких генераторов прозы,
   шаблонов «N шагов + 3 варианта», условий по имени в тексте, JSON-дампов.
3. **Тест качества** (жёсткий стандарт, §9): `KVEST_QUALITY_FILES=chapter3/<файл части>.ts npx vitest run src/content/quality.test.ts` —
   зелёный, включая «прохождение как игрок».
4. **Стенограмма — прочитать ЦЕЛИКОМ, как игрок**:
   `KVEST_TRANSCRIPT=farm KVEST_FROM=5 KVEST_WANT=hof_luedemann KVEST_TOGETHER=1 KVEST_ANSWERS=meet=b_to_a,shelter=farm,day2=farm,day3=farm npx vitest run src/content/transcript.test.ts`
   → `transcripts/farm-<сид>.txt` (3 прохождения; переменные — в шапке `transcript.test.ts`; `KVEST_POLICY=hasty` — игрок,
   который спешит). Для сравнения так же снять стенограмму главы 2 (`KVEST_FROM=3`) и прочитать кусок подряд — это эталон.
   В сводке в начале файла: шагов на участок (ориентир 30–60), экранов с выбором 3+ (большинство), экранов с единственной
   кнопкой (почти ноль), прерываний (≥ 2), **минимальная температура тела** (≥ 36; ниже — где-то «улица» под крышей).
5. **Самооценка** — таблица ниже, честно, с цитатами из стенограммы. Любая оценка < 4 — переписать и повторить с шага 3.
   Таблицу с цитатами положить в `CHAPTER<N>_VALIDATION.md` (раздел части).

### 8.3. Как ставить оценки (5 — уровень глав 1–2)

| Пункт | 5 — как в главах 1–2 | 3 и ниже — так было в прошлых версиях главы 3 |
|---|---|---|
| Структура | Сцены — места и эпизоды, у места тексты на каждое время суток; эпизод — 1–2 сцены, выбор на первом экране | Генератор по формуле, все эпизоды одной формы и в одно время; хабы-склады мелочей |
| Объём и плотность | 30–60 действий на участок, почти каждое — с человеком или последствием | Половина действий — «Проверить/Убрать/Положить», клики «дальше» |
| Напряжение и выборы | За участок хотя бы 2 раза «не по себе»; хотя бы один выбор, где можно потерять вещь, здоровье, человека или место | Цена выбора — ±3 доверия и усталость; сильное событие решено одной кнопкой и забыто через минуту |
| Решения на точках | Меняют где/с кем/что у вас; варианты с конкретными людьми, которых игрок видел; тяжёлый размен; исход виден в следующем участке | «Отдать пачку / остаться»; одинаковые решения два раза; «больному», «тому, кто слабее» без лица |
| Стиль и голоса | Почти в каждом тексте человек: реплика или жест с характером; последняя фраза — удар; голоса по WRITING_GUIDE §2 | Руки и предметы (ткань, щепка, шов); тики «больше не…», «сухой…»; канцелярит; неуклюжие обороты |
| Техника | Тесты, стенограммы без провалов, время/холод/мёртвые NPC верны, исходники читаются | Дампы, магические минуты, «улица» на кухне, флаги, которые никто не читает |

Вопросы, которые задаёт себе ревьюер, читая стенограмму (задай их себе):
* Где мне было не по себе? Где я колебался с выбором? (Если нигде — участок не готов.)
* Что я потерял или рискнул потерять? Кто это запомнил и где я об этом узнаю?
* Сколько текстов подряд без живого человека? (Больше трёх — плохо.)
* Самое сильное событие участка — сколько экранов ему отдано и что после него изменилось?
* Можно ли угадать, что будет на следующем экране? (Если всегда — формула.)
* Прочитай вслух три случайных текста: звучат ли они как `c2_farm`, `c4_messe`, `b2_svenja`?

## 9. Жёсткий стандарт (обязателен, обойти нельзя)

`src/content/quality.test.ts` — порог, ниже которого глава **не принимается**, как бы хорошо она ни выглядела по описанию.
Он проверяет и текст, и игру:
* **текст**: быт ≤ 6 % подписей; прямая речь ≥ 25 % текстов; тики ≤ 3 %; ни одной заготовки «улица или двор»; фразы в среднем
  5–10 слов; повторов текста между сценами ≤ 2 %; подписи ≤ 10 слов;
* **рукопись, а не генератор**: id каждой сцены и каждый текст есть в исходниках буквально (циклы, `c${n}_…`, склейка текста
  из кусков — провал); исходники как в главе 2, не JSON-дамп;
* **мир**: «под крышей» — не улица; флагов, которые никто не читает, ≤ 15 %;
* **прохождение как игрок** (16 пар, `playtest.ts`): в каждом новом участке медиана ≥ 30 шагов (у 10 % — ≥ 15),
  ≥ 2 событий-прерываний, ≥ 2 экранов с риском (`risky`, проверка навыка, травма), ≤ 6 экранов с единственной кнопкой,
  температура тела ≥ 36, ни одного тупика.

**Защищённые файлы** — `src/content/quality.test.ts`, `playtest.ts`, `transcript.test.ts`, `compat.test.ts`, `fixtures/`,
`docs/hidden/CHAPTER_GUIDE.md`, `docs/hidden/WRITING_GUIDE.md`, `AGENTS.md`, `.github/`. В ветке главы их **не менять**:
проверка PR (`.github/workflows/quality.yml`) берёт их из main и падает, если ветка их изменила. Нужна новая возможность
проверки — написать об этом в `CHAPTER<N>_VALIDATION.md`, её добавят в main. Перед работой: `git merge origin/main`.

Порог — минимум, а не цель: зелёный тест не означает уровень глав 1–2. Окончательная оценка — по стенограммам и таблице §8.3.
Часть, не прошедшая порог, не коммитится как «часть K»; глава с красным порогом не сливается.
